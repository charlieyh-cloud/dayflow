# DayFlow 개발 — Claude Code 5단계 프롬프트

> 각 단계를 **하나씩 순서대로** 실행하세요. 한 번에 여러 단계를 넣으면 컨텍스트가 흐려지고 결과 품질이 떨어집니다.

---

## 시작 전 준비 (1회만)

### 1. 리포지터리 및 PRD 배치

```bash
mkdir dayflow && cd dayflow
git init
mkdir -p docs
# 앞서 만든 PRD를 docs/prd.md 로 복사
claude
```

### 2. CLAUDE.md 생성 프롬프트

프로젝트 규칙을 먼저 세팅해야 이후 모든 단계에서 일관성이 유지됩니다.

```
docs/prd.md 를 읽고, 이 프로젝트의 CLAUDE.md 를 작성해줘.

포함할 내용:
- 프로젝트 한 줄 요약과 핵심 제약(PWA, 오프라인 우선, 접근성 WCAG 2.2 AA)
- 기술 스택: React + TypeScript + Vite, Workbox, IndexedDB(Dexie), TanStack Query
- 디렉터리 구조 규칙 (PRD 8.1 참조)
- 코딩 컨벤션: 함수형 컴포넌트, named export, 절대경로 import(@/)
- 접근성 규칙 (필수 준수):
  * 시맨틱 HTML 우선, ARIA는 필요한 곳에만
  * 모든 인터랙티브 요소는 키보드 접근 가능
  * 색상만으로 정보 전달 금지 — 아이콘/텍스트 병기
  * 터치 타겟 최소 44x44px
  * 크기 단위는 px 대신 rem
  * 동적 변경은 aria-live로 안내
- 커밋 컨벤션: Conventional Commits (feat/fix/a11y/perf/refactor/test/docs/chore/ci)
- 하지 말아야 할 것: localStorage 대신 IndexedDB 사용, any 타입 금지,
  API 키를 클라이언트 코드에 두지 않기

간결하게 작성해줘. 장황한 설명 말고 규칙 위주로.
```

**진행 팁**
- 각 단계 시작 전 `/clear` 로 컨텍스트를 비우세요.
- 큰 단계는 `Shift+Tab` 으로 **Plan Mode**를 켜고 계획을 먼저 검토한 뒤 실행하세요.
- 각 단계 종료 시 반드시 커밋하고 푸시하세요. 롤백 지점이 됩니다.

# STEP 1 — 프로젝트 기반 + PWA 셸 + GitHub CI/CD

**목표**: 코드를 쓰기 전에 "잘못된 코드가 병합되지 않는 환경"을 먼저 만든다. 특히 접근성 검사를 CI 게이트로 걸어둔다.

```
docs/prd.md 의 6장(기술 요구사항)과 8장(개발 및 배포 워크플로우)을 읽고,
프로젝트 기반 구조와 CI/CD를 구축해줘.

## 1. 프로젝트 초기화
- Vite + React + TypeScript 프로젝트 생성
- PRD 8.1의 디렉터리 구조 그대로 생성 (src/features 하위 폴더 포함)
- 절대경로 import 별칭(@/) 설정
- ESLint + Prettier + eslint-plugin-jsx-a11y 설정
- husky + lint-staged + commitlint 설정 (Conventional Commits 강제)

## 2. PWA 셸
- vite-plugin-pwa (Workbox) 설정
- public/manifest.webmanifest 작성:
  name, short_name, start_url, scope, display: standalone,
  theme_color, background_color, 아이콘(192/512/maskable)
- Service Worker 기본 골격:
  * 앱 셸 precache
  * 정적 에셋 stale-while-revalidate
  * 업데이트 감지 → "새 버전이 있습니다" 배너 컴포넌트
- 오프라인 폴백 페이지
- 중요: sw.js 는 no-cache 헤더 전제로 구성할 것

## 3. 디자인 토큰 및 접근성 기반
- CSS 변수로 색상 토큰 정의 (라이트/다크/고대비 3종)
- 모든 텍스트 색 조합이 4.5:1, UI 컴포넌트가 3:1 이상 대비를 만족하도록 값 선정
- rem 기반 타이포그래피 스케일
- prefers-reduced-motion, prefers-color-scheme 대응
- 공통 컴포넌트: Button, Input, Select, Checkbox, Modal, Toast
  → 전부 키보드 접근 가능, 포커스 링 표시(3:1 이상), 44x44px 최소 타겟
  → Modal은 포커스 트랩 + Esc 닫기 + 열기 전 포커스 복원
- "본문 바로가기" 스킵 링크와 랜드마크 구조(header/nav/main)

## 4. 테스트 환경
- Vitest + Testing Library 설정
- jest-axe 설정 및 공통 컴포넌트 접근성 테스트 작성
- Playwright 설정 (기본 스모크 테스트만)

## 5. GitHub Actions
- .github/workflows/ci.yml : PRD 8.4의 8단계 전부 구현
  (lint → typecheck → unit → e2e → axe → lighthouse-ci → size-limit → build)
  * axe critical/serious 위반 1건이라도 있으면 실패
  * Lighthouse Accessibility 100점 미만이면 실패
- .github/workflows/deploy.yml : main 병합 시 배포
- PR 템플릿 (접근성 확인 체크리스트 포함)
- 이슈 템플릿, .env.example, .gitignore

## 완료 조건
- npm run dev 로 실행되고 브라우저에서 PWA 설치 가능
- npm run build && npm run preview 로 오프라인 동작 확인
- 모든 CI 스크립트가 로컬에서 통과
- Lighthouse Accessibility 100점

작업 후 Conventional Commits 규칙에 맞춰 여러 개의 논리 단위로 커밋해줘.
```

**검증 후 실행**
```
GitHub에 리포지터리를 만들고 push한 뒤, Actions가 통과하는지 확인해줘.
실패하면 원인을 찾아서 고쳐줘.
```

# STEP 2 — 데이터 모델 + 일정 CRUD + 카테고리 (오프라인 우선)

**목표**: 서버 없이도 완전히 동작하는 로컬 앱을 먼저 완성한다. 백엔드는 4단계에서 붙인다.

```
docs/prd.md 의 4.1(일정 관리), 4.3(카테고리), 5장(데이터 모델)을 읽고,
로컬에서 완전히 동작하는 일정 관리 기능을 구현해줘.
아직 서버는 붙이지 않는다. IndexedDB만 사용한다.

## 1. 데이터 계층
- Dexie로 IndexedDB 스키마 구현 (PRD 5장의 모델 그대로)
  Task, Subtask, Category, Reminder, User preferences
- 인덱스: (startAt), (categoryId, status), (updatedAt)
- 모든 레코드에 createdAt, updatedAt, deletedAt, syncVersion 포함
  → 삭제는 물리 삭제가 아닌 soft delete (4단계 동기화 대비)
- 시드 데이터: 기본 카테고리 5종(개인/업무/건강/학습/가족)
- TypeScript 타입을 단일 소스(src/types)로 정의

## 2. 일정 CRUD
- 생성/조회/수정/삭제 전체 구현
- 속성: 제목, 메모, 시작/종료일시, 종일 여부, 시간미지정(isTimeless),
  카테고리, 우선순위(긴급/높음/보통/낮음), 상태, 장소(필드만), 서브태스크
- 반복 일정: RRULE 파싱/생성 (rrule 라이브러리)
  → 수정 시 "이 일정만 / 이후 모든 / 전체" 선택 다이얼로그
- 삭제 시 10초 Undo 토스트

## 3. 카테고리 관리
- 사용자 정의 카테고리 CRUD (이름, 색상, 아이콘)
- 다중 선택 필터
- 사용 중인 카테고리 삭제 시 이관/함께삭제 선택 다이얼로그
- 중요: 카테고리는 색상만으로 구분하지 말고 반드시 아이콘 + 텍스트 레이블 병기

## 4. 일정 생성/편집 폼
- 모든 입력에 명시적 label 연결
- 필수값 검증, 오류는 텍스트로 원인과 해결 방법 안내
- 오류 발생 시 첫 오류 필드로 포커스 이동, aria-describedby 연결
- 저장 성공은 aria-live로 안내
- 날짜/시간 선택기는 반드시 키보드로 직접 입력도 가능해야 함
  (네이티브 input[type=datetime-local] 우선 검토)

## 완료 조건
- 앱을 완전히 오프라인으로 두고도 일정 등록/수정/삭제/필터가 모두 동작
- 새로고침해도 데이터 유지
- 마우스를 쓰지 않고 키보드만으로 일정 생성 → 수정 → 삭제 전체 플로우 완주 가능
- 데이터 계층 단위 테스트 + 폼 접근성 테스트 통과

각 기능 단위로 커밋해줘.
```

# STEP 3 — 뷰 + 진행 상황 체크 + 대시보드

**목표**: 데이터를 "보는 방식"을 완성한다. 캘린더 UI는 접근성 난이도가 가장 높은 구간이므로 여기에 시간을 쓴다.

```
docs/prd.md 의 4.2(뷰 및 탐색), 4.4(진행 상황 체크), 4.8(접근성)을 읽고
화면을 구현해줘.

## 1. 뷰 구현
- 오늘(Today): 기본 진입 화면. 현재 시각 기준 지금/다음 일정 강조, 미완료 상단
- 일간 타임라인: 24시간 세로 그리드, 겹치는 일정 병렬 배치
- 주간: 7일 x 시간 그리드
- 월간: 날짜별 요약 도트, 탭 시 해당 일 상세
- 목록: 시간 무관 할 일 + 정렬(마감임박/우선순위/카테고리)
- 뷰 전환: 상단 세그먼트 컨트롤 + 좌우 스와이프
- 카테고리 필터는 뷰를 바꿔도 유지

## 2. 캘린더 접근성 (가장 중요, 대충 넘기지 말 것)
- 월간 뷰는 role="grid" 로 구성, 방향키로 날짜 이동,
  PageUp/PageDown으로 월 이동, Home/End로 주의 시작/끝
- 로빙 tabindex 패턴 적용 (그리드 전체가 tab stop 1개)
- 각 날짜 셀은 스크린리더로 "10월 15일 목요일, 일정 3개, 2개 완료" 처럼 읽히도록
- 일정 블록은 색상 외에 텍스트로도 카테고리/우선순위 식별 가능해야 함
- 뷰 전환 시 변경 내용을 aria-live로 안내

## 3. 드래그 조작과 그 대안 (WCAG 2.2 필수)
- 데스크톱: 드래그로 시간 이동/길이 조절
- 모바일: 롱프레스 후 이동
- 반드시 함께 제공: 드래그를 쓰지 않고 컨텍스트 메뉴 또는 편집 폼에서
  시간을 변경하는 경로. 드래그가 유일한 수단이 되면 안 됨

## 4. 진행 상황 체크
- 상태 전이: 예정 → 진행중 → 완료 / 연기 / 취소
- 원탭 완료 체크박스, 완료 시 시각 피드백 + aria-live 안내
- 서브태스크 완료 비율 자동 계산
- 미완료 일정 다음날 자동 이월 (설정에서 on/off)

## 5. 대시보드
- 주간 완료율 추이, 카테고리별 분포, 연속 달성일(스트릭)
- 중요: 모든 차트는 그래프 + 수치 텍스트를 함께 제공
  차트에는 요약 텍스트 대안(예: 표 형태) 제공
- 진행률 바는 role="progressbar" + aria-valuenow/valuemin/valuemax

## 완료 조건
- 5개 뷰 전부 키보드만으로 탐색 가능
- 스크린리더(VoiceOver 또는 NVDA)로 월간 뷰에서 날짜 이동과 일정 확인 가능
- 텍스트 200% 확대 시 가로 스크롤이나 콘텐츠 손실 없음
- axe 검사 critical/serious 0건
- Lighthouse Accessibility 100점 유지

구현 후 접근성 자가 점검 결과를 표로 정리해서 알려줘.
```

# STEP 4 — 백엔드 + 인증 + 동기화 + 백그라운드 푸시

**목표**: 웹/모바일 연동과 알림을 완성한다. PRD의 핵심 가치가 실제로 작동하기 시작하는 단계.

```
docs/prd.md 의 4.5(알림·리마인더, 특히 4.5.1 백그라운드 푸시 동작 방식),
4.9(PWA/동기화), 4.10(계정 및 설정), 8.6(시크릿 관리)을 읽고 구현해줘.

## 1. 백엔드 및 인증
- Supabase 기준으로 구현 (다른 선택지가 낫다면 먼저 제안하고 확인받을 것)
- PRD 5장 모델대로 테이블 생성 + RLS 정책 (사용자는 자기 데이터만 접근)
- 인증: 이메일 매직링크 + Google 소셜 로그인
- 마이그레이션 파일을 리포지터리에 포함

## 2. 양방향 동기화
- IndexedDB(로컬) ↔ 서버 델타 동기화 (updatedAt 기준)
- 낙관적 업데이트: UI를 먼저 반영하고 백그라운드로 전송
- Background Sync API로 오프라인 변경분 큐잉 → 온라인 복귀 시 자동 전송
  (미지원 브라우저는 온라인 이벤트 리스너로 폴백)
- 충돌 해결: syncVersion 비교, 기본 Last-Write-Wins,
  동일 일정 동시 수정 시 사용자 선택 UI 제공
- 오프라인 상태와 동기화 대기 건수를 UI에 표시
- 실시간 반영(Supabase Realtime), 목표 지연 3초 이내

## 3. 백그라운드 푸시 (PRD 4.5.1 그대로 구현)
- VAPID 키 생성, PushSubscription을 기기 단위로 서버 저장
- 서버 스케줄러(크론)가 reminder 시각에 푸시 발송
  → 발송 시각 판단은 반드시 서버가 한다. 클라이언트 타이머 사용 금지
- Service Worker push 핸들러:
  * 반드시 showNotification 호출 (silent push 금지 — 구독 해지됨)
  * 표시 직전 일정 최신 상태 확인, 이미 완료/삭제된 일정은 표시하지 않음
  * 동일 일정은 tag로 중복 방지, renotify로 대체
  * payload에 일정 요약 데이터를 포함시켜 로컬 캐시 갱신
- notificationclick: 해당 일정으로 딥링크. 열린 탭 있으면 clients.matchAll → focus
- 알림 액션 버튼: 완료 / 10분 미루기 / 열기
  → 앱을 열지 않고 Service Worker에서 API 호출로 처리
- pushsubscriptionchange 이벤트에서 자동 재구독
- Periodic Background Sync로 12시간 간격 사전 페치 (미지원 시 폴백)
- Badging API로 오늘 남은 미완료 수 표시 (미지원 시 인앱 배지)

## 4. 알림 UX
- 권한 요청은 앱 진입 시가 아니라 사용자가 첫 알림을 설정하는 시점에
- 권한 거부 시 브라우저 설정에서 복구하는 방법 안내 화면
- iOS 미설치 사용자에게 설치 안내 배너 (Web Push는 설치 시에만 동작)
- 설정: 알림 시점 기본값, 카테고리별 규칙, 방해금지 시간대, 일일 브리핑
- 설정 화면에 현재 푸시 구독 상태를 명확히 표시

## 5. 시크릿
- VAPID 키 등 모든 키는 .env + GitHub Secrets. 코드에 하드코딩 금지
- .env.example 갱신
```

```
## 1. 챗봇
- LLM API는 반드시 서버 프록시 경유. 클라이언트에 키 노출 금지

  절대 자동 저장하지 않는다
```
