| 항목 | 내용 |
|---|---|
| 문서 버전 | v0.1 (Draft) |

| 상태 | 검토 요청 |

---

## 1. 배경 및 문제 정의

기존 To-Do 앱은 대부분 "목록 관리"에 머물러 있어, 실제 하루를 살아내는 흐름과 어긋난다. 사용자는 다음 지점에서 이탈한다.

- 할 일은 적어두지만 **언제 할지**가 없어 실행되지 않는다.
- 개인/업무 일정이 한 화면에 섞여 맥락 전환 비용이 크다.
- 장소가 있는 일정(미팅, 병원, 약속)에서 앱을 벗어나 지도 앱을 따로 열어야 한다.
- 일정 입력 자체가 번거로워 기록을 포기한다.

DayFlow는 **날짜·시간 기반 일정 관리 + 카테고리 분리 + 대화형 입력 + 장소 이동 지원**을 하나의 PWA로 묶어 "기록 → 알림 → 이동 → 완료"까지의 실행 루프를 끊김 없이 만든다.

## 2. 목표

### 2.1 제품 목표
1. 일정 등록에 걸리는 시간을 **10초 이내**로 줄인다 (챗봇 입력 기준).
2. 등록된 일정의 **완료율(체크율)** 을 사용자에게 가시화하고 개선한다.
3. 웹/모바일 어디서 접속해도 **동일한 데이터와 경험**을 제공한다.
4. 접근성을 부가 기능이 아닌 **기본 설계 조건**으로 삼는다 (WCAG 2.2 AA).

### 2.2 비목표 (Out of Scope, v1)
- 팀 협업 / 일정 공유 / 권한 관리
- 프로젝트 간트차트, 칸반 보드
- 자체 지도 렌더링 엔진 (외부 지도 API 연동으로 대체)
- 네이티브 앱 스토어 배포 (PWA 우선, 추후 검토)

### 2.3 성공 지표 (KPI)

| 지표 | 목표 (출시 3개월) |
|---|---|
| D7 리텐션 | 35% 이상 |
| 주간 활성 사용자당 일정 등록 수 | 12건 이상 |
| 일정 완료 체크율 | 60% 이상 |
| 챗봇 경유 일정 등록 비중 | 전체 등록의 30% 이상 |
| PWA 홈 화면 설치율 | 활성 사용자의 40% 이상 |
| 접근성 자동 검사 위반 (axe critical) | 0건 |

#### 4.5.1 백그라운드 푸시 동작 방식

앱이 **완전히 닫혀 있는 상태에서도** 사용자가 일정을 미리 확인할 수 있어야 한다. 다음 3개 계층을 조합한다.

**① 서버 스케줄링 + Web Push (핵심, P0)**

```
[알림 스케줄러(서버 크론)]
        │  일정의 reminder 시각 도달
        ▼
[Push Service (FCM / APNs / Mozilla)]  ← VAPID 서명
        ▼
[Service Worker: push 이벤트]
        ▼
  showNotification() → 사용자 기기에 표시
```

- 알림 발송 시각 판단은 **클라이언트가 아닌 서버**가 담당한다. 기기가 꺼져 있거나 브라우저가 종료돼도 발송이 보장된다.
- Service Worker의 `push` 이벤트 핸들러는 **반드시 알림을 표시**해야 한다 (표시 없는 silent push는 브라우저가 구독을 해지시킴).
- `notificationclick` 이벤트에서 해당 일정 상세 화면으로 딥링크 이동. 이미 열린 탭이 있으면 재사용(`clients.matchAll` → `focus`).
- 알림 액션(`완료`/`10분 미루기`)은 앱을 열지 않고 Service Worker에서 API를 호출해 처리한다.
- 구독 정보(`PushSubscription`)는 서버에 기기 단위로 저장하고, 만료(`pushsubscriptionchange`) 시 자동 재구독한다.

**② 백그라운드 사전 페치 (P1)**

- **Periodic Background Sync API**로 하루 수 회 다가올 일정을 미리 받아 IndexedDB에 캐시한다. 사용자가 앱을 열었을 때 네트워크 없이도 최신 일정이 보인다.
- 지원 브라우저가 제한적(Chromium 계열, 설치된 PWA + engagement 조건)이므로 **보조 수단**으로만 사용한다. 미지원 환경은 푸시 수신 시 함께 전달되는 payload로 캐시를 갱신한다.
- 푸시 payload에는 알림 문구뿐 아니라 **해당 일정의 요약 데이터**를 포함시켜, 알림 도착만으로도 로컬 캐시가 최신화되도록 한다.

**③ 오프라인 액션 큐 (P1)**

- **Background Sync API**로 오프라인 상태에서의 완료 체크·수정을 큐에 넣고, 네트워크 복구 시 자동 전송한다.

**설계 원칙**
- 알림은 서버가 보낸 시각을 신뢰하되, Service Worker는 표시 직전 **일정의 최신 상태를 확인**한다. 이미 완료·삭제된 일정의 알림은 표시하지 않는다.
- 동일 일정에 대한 알림은 `tag`를 지정해 중복 누적을 방지하고, 최신 알림으로 대체(`renotify`)한다.
- 배터리·데이터 사용을 고려해 사전 페치 주기는 최소 12시간 간격, Wi-Fi 우선으로 제한한다.

**제약 사항 (명시 필요)**
- iOS Safari의 Web Push는 **홈 화면에 추가된 PWA에서만** 동작한다. 미설치 iOS 사용자에게는 설치 안내 배너를 노출하고, 대체 수단으로 인앱 알림 + 이메일 리마인더를 제공한다.
- iOS/Safari는 **Periodic Background Sync 및 Background Sync를 지원하지 않는다.** 해당 환경에서는 푸시 payload 기반 캐시 갱신 + 앱 포그라운드 진입 시 즉시 동기화로 대체한다.
- Badging API는 설치된 PWA 및 일부 브라우저에서만 동작하므로, 미지원 시 인앱 배지로 대체한다.
- 알림 권한은 최초 진입 시가 아니라 **사용자가 첫 알림을 설정하는 시점**에 요청한다 (권한 수락률 향상).
- 권한이 거부된 경우 재요청이 불가하므로, 브라우저 설정에서 복구하는 방법을 안내하는 화면을 제공한다.

**기능별 지원 매트릭스**

| 기능 | Chrome/Edge (Android·Desktop) | Safari (iOS, 설치 시) | Safari (iOS, 미설치) |
|---|---|---|---|
| Web Push | ✅ | ✅ | ❌ (이메일 폴백) |
| 알림 액션 버튼 | ✅ | 제한적 | ❌ |
| Periodic Background Sync | ✅ (조건부) | ❌ | ❌ |
| Background Sync | ✅ | ❌ | ❌ |

### 4.6 챗봇 (F-06)

**목적**: 폼 입력을 대체하는 가장 빠른 입력 수단이자, 일정 조회의 자연어 인터페이스.

| ID | 요구사항 |
|---|---|
| F-06-1 | 자연어 일정 등록: "내일 오후 3시에 강남에서 팀 미팅" → 구조화된 일정 생성 |
| F-06-2 | 파싱 결과를 **확인 카드**로 먼저 보여주고 사용자가 수정/확정 (자동 저장 금지) |
| F-06-3 | 자연어 조회: "이번 주 업무 일정 알려줘", "내일 뭐 있어?" |
| F-06-4 | 일정 변경/삭제 명령 지원, 삭제는 반드시 확인 단계를 거침 |
| F-06-5 | 음성 입력 (Web Speech API) — 미지원 브라우저에서는 버튼 비노출 |
| F-06-6 | 대화 맥락 유지 (직전 일정 참조: "그거 1시간 미뤄줘") |
| F-06-7 | 실패 시 폴백 — 파싱 불가 시 부분 인식 결과를 채운 편집 폼으로 전환 |

**모호성 처리**: 날짜/시간이 불명확하면("다음 주쯤") 되묻는다. 임의 추정으로 저장하지 않는다.

**대화 UI 접근성**: 새 메시지는 `aria-live="polite"` 영역으로 전달, 대화 로그는 키보드로 탐색 가능해야 한다.

**접근성 대응**: 지도는 시각 정보에 의존하므로, 동일한 정보를 **텍스트로 병기**한다 (주소 전체, 예상 소요 시간, 도보/대중교통 요약). 지도 영역에는 적절한 대체 텍스트와 "텍스트로 경로 보기" 버튼을 제공한다.

### 4.8 접근성 (F-08) — 전 기능 공통 필수 요건

목표 수준: **WCAG 2.2 Level AA 준수**, 한국 웹 접근성 인증(KWCAG 2.2) 기준 충족.

## 8. 개발 및 배포 워크플로우 (GitHub)

모든 소스는 GitHub 리포지터리에서 관리하며, **커밋 → 푸시 → 자동 검증 → 자동 배포** 흐름을 기본으로 한다.

### 8.1 리포지터리 구조

```
dayflow/
├── .github/
│   ├── workflows/
│   │   ├── ci.yml              # lint · test · a11y · build
│   │   ├── deploy.yml          # main 병합 시 프로덕션 배포
│   │   └── preview.yml         # PR별 프리뷰 배포
│   ├── ISSUE_TEMPLATE/
│   └── pull_request_template.md
├── public/
│   ├── manifest.webmanifest
│   ├── sw.js                   # Service Worker (푸시·캐싱·백그라운드 동기화)
│   └── icons/
├── src/
│   ├── components/
│   ├── features/               # tasks · categories · chat · map · notifications
│   ├── lib/
│   └── db/                     # IndexedDB 스키마
├── server/                     # API · 알림 스케줄러
├── tests/
│   ├── unit/
│   ├── e2e/                    # Playwright
│   └── a11y/                   # axe-core 시나리오
└── docs/
    └── prd.md
```

### 8.2 브랜치 전략

| 브랜치 | 용도 | 배포 대상 |
|---|---|---|
| `main` | 항상 배포 가능한 상태 | 프로덕션 |
| `develop` | 통합 개발 브랜치 | 스테이징 |
| `feature/*` | 기능 단위 작업 | PR 프리뷰 |
| `fix/*` | 버그 수정 | PR 프리뷰 |
| `hotfix/*` | 긴급 수정 (main 직접 분기) | 프로덕션 |

- `main`과 `develop`은 **직접 푸시 금지** (branch protection). PR + 리뷰 1인 승인 + CI 통과 후에만 병합.
- 병합 방식은 Squash Merge를 기본으로 하여 히스토리를 선형으로 유지한다.

### 8.3 커밋 컨벤션

Conventional Commits 규칙을 따른다.

```
<type>(<scope>): <subject>

feat(notifications): 백그라운드 푸시 수신 핸들러 구현
fix(sw): 알림 클릭 시 중복 탭 열리는 문제 수정
a11y(calendar): 주간 뷰 키보드 탐색 순서 수정
chore(deps): workbox 7.1 업그레이드
```

**type**: `feat` / `fix` / `a11y` / `perf` / `refactor` / `test` / `docs` / `chore` / `ci`
**scope 예시**: `tasks`, `categories`, `notifications`, `sw`, `chat`, `map`, `sync`, `auth`

- commitlint + husky로 커밋 시점에 규칙을 강제한다.
- pre-commit 훅에서 ESLint · Prettier · 타입 체크를 실행한다.
- 커밋 메시지에 관련 이슈 번호를 포함한다 (`Closes #42`).

### 8.4 CI 파이프라인 (`ci.yml`)

푸시 및 PR 생성 시 자동 실행. 하나라도 실패하면 병합 불가.

| 단계 | 도구 | 실패 조건 |
|---|---|---|
| 1. 린트 | ESLint + Prettier | 오류 1건 이상 |
| 2. 타입 체크 | TypeScript `--noEmit` | 오류 1건 이상 |
| 3. 단위 테스트 | Vitest | 실패 또는 커버리지 70% 미만 |
| 4. E2E 테스트 | Playwright | 핵심 플로우 실패 |
| 5. **접근성 검사** | axe-core (jest-axe / Playwright) | critical·serious 위반 1건 이상 |
| 6. Lighthouse CI | lighthouse-ci | Accessibility 100 / PWA 통과 / Performance 90 미만 시 실패 |
| 7. 번들 크기 | size-limit | 앱 셸 200KB(gzip) 초과 |
| 8. 빌드 | Vite build | 빌드 실패 |

> 접근성은 리뷰어의 재량이 아니라 **파이프라인 게이트**로 강제한다. 자동 검사가 잡지 못하는 항목(스크린리더 흐름, 포커스 순서)은 PR 템플릿의 체크리스트로 보완한다.

### 8.5 배포 (`deploy.yml`)

- `main` 병합 시 자동 빌드 후 프로덕션 배포. `develop` 병합 시 스테이징 배포.
- PR 생성 시 프리뷰 URL 자동 생성 및 코멘트 등록 → 실기기에서 PWA 설치·푸시 테스트 가능.
- 배포 후 Service Worker 갱신 확인, 실패 시 직전 커밋으로 자동 롤백.
- 태그 기반 릴리스: `v1.0.0` 태그 푸시 시 릴리스 노트 자동 생성.

**PWA 배포 시 주의**
- Service Worker(`sw.js`)에는 **캐시 헤더를 적용하지 않는다** (`no-cache`). 갱신이 반영되지 않는 문제의 주원인.
- 빌드마다 캐시 버전을 갱신하여 구버전 에셋이 남지 않게 한다.
- GitHub Pages를 사용할 경우 서브경로 배포에 맞춰 `manifest`의 `start_url`·`scope`와 Service Worker 등록 경로를 조정한다.

### 8.6 시크릿 관리

- VAPID 키, LLM API 키, 지도 API 키, DB 접속 정보는 **GitHub Secrets**로 관리하며 리포지터리에 커밋하지 않는다.
- `.env.example`만 커밋하고 실제 `.env`는 `.gitignore` 처리.
- LLM·지도 API 호출은 클라이언트에서 직접 하지 않고 **서버 프록시**를 경유해 키 노출을 차단한다.
- Dependabot 및 CodeQL(보안 스캔)을 활성화한다.

### 8.7 이슈 및 진행 관리

- GitHub Issues + Projects(칸반)로 백로그 관리.
- 라벨 체계: `type:feat` / `type:bug` / `priority:P0~P2` / `area:notifications` / `a11y` / `good-first-issue`
- PR 템플릿 필수 항목: 변경 요약, 관련 이슈, 테스트 방법, **접근성 확인 체크리스트**(키보드 조작 / 스크린리더 / 대비 / 포커스), 스크린샷.
